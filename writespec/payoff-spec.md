# 爽点兑现规范

本规范是爽点定义、等级、密度档、规划契约、正文证据和门禁路由的唯一权威。`world/hooks.md` 管理未解决问题与伏笔生命周期；爽点管理读者承诺是否获得可感回报，两者不得混用。

## INV-PAYOFF-001 爽点兑现与升级

启用爽点治理后的新章或已发布章节新修订，必须绑定合法密度档，形成至少一个跨场景持续的章节主爽点，并以正文证据证明“承诺/压力 -> 主角主动行动 -> 可信代价 -> 有利状态变化 -> 外部确认或后果”已经闭合。缺少主爽点、密度不足、同一事件拆分计数、承诺到期未兑现、收益类型长期重复或滚动高潮逾期均为 `FAIL`；不得用钩子、伏笔、危机、旁人空喊震惊或旁白宣布变强替代兑现。

适用范围：

- 新初始化 World Bible 的冻结章节契约。
- `修订卷规划 ARC-NNN` 后重新冻结的未发布章节契约。
- 非追溯启用边界之后执行的 `构思第 N 章` 与 `创作第 N 章`。
- `创作第 N 章` 对已发布目标创建的新 `RNN` 修订。

既有正式章节和未声明 `payoff_policy` 的既有冻结契约不追溯判错。启用后的滚动窗口从 `activation_chapter` 起算，不得拿启用前章节补数或扣分。

## 1. 爽点成立条件

爽点是读者承诺获得回报的事件，不等于单纯胜利、场面破坏或配角反应。有效爽点必须同时具备：

1. `promise`：此前建立的具体读者期待或压力。
2. `action`：主角以判断、选择或行动促成结果。
3. `state_delta`：能力、资源、身份、关系、信息、自由度或敌我局势产生有利变化。
4. `recognition`：对手、旁观者、制度、环境或后续行动确认结果有效。
5. `cost`：与作品力量和资源规则一致的代价、风险或机会成本。

同一 `event_key` 只能计作一个爽点。“出拳、碎石、众人震惊”属于同一事件；反应只用于确认结果，不能另计。信息揭示只有在赋予主角行动优势时才属于爽点；单纯抬出新谜题属于牵引或钩子。

## 2. 等级

| 等级 | 判定 |
| :--- | :--- |
| 微回报 | 改变当前场景的局部优势，可以只持续到场景结束 |
| 章节主爽点 | 完成本章核心承诺，状态变化至少持续到下一章 |
| 小高潮 | 关闭约 2-3 章的短冲突，至少形成两项持续状态变化 |
| 大爽点 | 完成阶段目标，改变能力层级、身份位置、资源基础、核心关系或敌我格局，并开启更高一级冲突 |

等级按影响范围判断，不按爆炸规模或旁观者数量判断。场面巨大但局势未变不能升格；取得唯一资格等安静事件若改变阶段位置，可以构成大爽点。

## 3. 类型与轮换

合法类型仅限：

- `POWER`：突破、压制或以既有规则越阶破局。
- `RESOURCE`：获得功法、道具、钱财、资格或机会。
- `STATUS`：扬名、晋升或获得有行动后果的认可。
- `REVERSAL`：洗冤、打脸、反杀或令敌方计划落空。
- `INFORMATION`：看破秘密并取得行动优势。
- `RELATIONSHIP`：赢得信任、保护成功或改变关系主动权。
- `AUTONOMY`：摆脱控制、拒绝屈辱或取得选择权。
- `COMPETENCE`：用专业判断解决他人无法解决的问题。

每章至少覆盖两类。相邻两章的主爽点类型不得相同；任意完整三章窗口至少覆盖三种主爽点类型。类型轮换不能替代因果、代价或升级证据。

## 4. 密度档

| 档位 | 章内目标 | 确定性下限 | 滚动节奏 |
| :--- | :--- | :--- | :--- |
| `standard` | 2-4 个微回报 + 1 个章节主爽点 | 至少 2 个有效爽点、2 种类型 | 每 3 章至少 1 个小高潮；每 12 章至少 1 个大爽点 |
| `high` | 3-5 个微回报 + 1 个章节主爽点 | 至少 3 个有效爽点、2 种类型 | 任意 2 章至少 1 次跨章升级；每 3 章至少 1 个小高潮；每 8 章至少 1 个大爽点 |

新书 CH-0001~CH-0010 和每卷开篇三章使用 `high`；其余默认 `standard`。`high` 章节第一次微回报应在正文前 20%-25% 出现，此项由语义门禁按段落位置判断，不以机械字符切割替代阅读判断。

超过建议上限不自动加分。为了达标而增加配角送脸、拆分同一事件、滥发奖励或降低对手智力，按虚假密度处理。

## 5. 规划契约

新初始化或经卷规划修订重新冻结的 `outline.md` 必须声明：

```yaml
payoff_policy:
  schema: novel-harness/payoff-policy/v1
  activation_chapter: 1
  default_profile: standard
  book_opening_high_through: 10
  volume_opening_high_count: 3
```

启用边界后的每个冻结章节必须包含 `payoff_contract`，至少记录 `profile`、`payoffs`、`primary_payoff_id`、`climax`、`escalation` 和 `escalation_from`。规划项使用稳定 `PAY-CH-NNNN-NN`，并为每个独立事件提供唯一 `event_key`。

旧大纲没有 `payoff_policy` 时仍可通过历史契约校验；但启用后的章节事务必须在 staging 生成本章契约和滚动证据。后续执行 `修订卷规划` 时，应把启用策略与剩余未发布章节计划正式写入候选大纲。

## 6. 正文证据

最终 staging 正文必须生成 `payoff-evidence.yaml`：

- `schema`: `novel-harness/payoff-evidence/v1`。
- `chapter_id`、`profile`、`mode` 和非追溯启用边界。
- 每个爽点的 ID、类型、`event_key`、承诺、行动、状态变化、确认、代价、持续范围及正文定位。
- `primary_payoff_id`。
- 从启用边界或最近大爽点起的 `rolling_window`，记录章节、主类型、高潮等级和升级范围。
- 已发布修订另记录原文 hash、下游影响和有效批准状态。

执行器先运行 `python scripts/validate_payoff.py <payoff-evidence.yaml>` 校验结构、计数、类型轮换和窗口，再由 `payoff-fulfillment` 语义门禁核对正文定位是否真实支撑上述字段。确定性通过不代表语义通过。

新建证据时使用 `templates/payoff-evidence-template.yaml`，替换示例值后保存到事务记录声明的 `evidence_path`；不得把示例内容当作当前章节证据。

## 7. 阶段职责

- World Bible 初始化/优化/卷规划：安排类型轮换、短循环和阶段大爽点，不用同一表现机制填满章节表。
- 构思：绑定密度档与爽点契约，明确各场景承诺和兑现，不得把章末牵引当成本章回报。
- 创作：把行动、代价、状态变化和确认写入正文，提交结构化证据。
- 读者评价：以相同爽点 ID 检查承诺落空、错位、重复和体感不足。
- 润色：只能强化已存在的动作因果、外部反应、节奏和情绪回响；不得新增事件或状态变化来补造爽点。
- World Bible 回写：`chapter-summary.md` 只保存已发布章节的主爽点类型、状态变化和证据摘要，不保存评分或规划提示。

## 8. 失败与路由

- `WARN_AUTO_FIX`：正文已有状态变化，但动作、确认或情绪回响不清；允许在 `chapter-polish.md` 边界内修复。
- `AUTO_ROUTE_COMMIT`：未发布当前章需要新增行动或调整结构，重新进入 `创作第 N 章` 候选并通过全部门禁。
- `AUTO_ROUTE_REVIEW`：需要修改后续契约、卷节奏、核心 World Bible，或对已发布章节新增事实；生成候选和影响审计后等待确认。
- `HUMAN_REQUIRED`：改变卷目标、核心金手指、既有发布事实的长期含义或接受不可逆风险。

## 9. 已发布章节修订

不新增命令。`创作第 N 章` 发现目标已发布时，进入 `published-revision` 条件模式并创建新 `RNN`：

1. 绑定正式正文基线和 hash。
2. 审计爽点缺口及所有下游章节、World Bible、线索和卷契约影响。
3. 生成正文差异、事实差异、下游影响和恢复点预览。
4. 取得明确批准；未经批准不得覆盖。
5. 影响未发布后续契约时联动 `修订卷规划 ARC-NNN` 候选；影响其他已发布章节时列出连续返工范围并停止单章提交。
6. 由事务执行器通过全部新章门禁后提交。

`润色章节 CH-NNNN` 始终保持等义呈现，不得借爽点治理扩大权限。

## 外部参考定位

`.idea/签约.txt` 是平台经验参考，不是规则权威。其“即时回报、黄金三章和减少纯悬念替代兑现”的建议，经本规范转化为可追踪契约与证据；具体数量以本规范的密度档为准。
